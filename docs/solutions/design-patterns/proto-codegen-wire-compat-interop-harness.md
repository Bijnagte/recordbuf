# Interop test harness: verify a protoc codegen plugin's output against protobuf-java

## Context

`recordbuf` generates Java records with a hand-rolled `Codec` that reads and
writes protobuf's binary wire format. The bug class is **silent**: a wrong
encoding (e.g. emitting a `fixed32` as a varint, or omitting a field tag) does
not throw — it just produces bytes the reference does not understand, corrupting
data on the wire. Unit tests that only assert "round-trips through my own
codec" will not catch divergence from the reference; they prove self-consistency,
not compatibility.

The durable answer: **prove byte- and semantic-equality of the generated codec
against protobuf-java's `com.google.protobuf.MessageLite`** using an automation
that runs both the recordbuf plugin and protobuf-java's own `protoc` plugin in
the same build.

## Guidance

Four structural ideas make the harness work:

### 1. Test the real wire, not your own codec

Generate the protobuf-java reference (`MessageLite` subclass) for the same
`.proto` and assert three properties on each, per field-type family:

- `byteEqual`: `record.Codec.encode(x)` **==** `Reference.newBuilder()...build().toByteArray()` (assertArrayEquals).
- `interopDecodesProtobuf`: `Record.Codec.decode(protobufJavaBytes)` **==** `the record` (equal, not just non-null).
- `roundTrip`: `record.Codec.decode(record.Codec.encode(x)) == x`.

Byte-equality is the strongest signal: if generated bytes equal protobuf-java's
`toByteArray()`, the codec is wire-compatible for that value.

### 2. One `.proto` per field-type family, in the TEST source set

A single growing `compat.proto` is fine, but one `.proto` **per family**
(`int.proto`, `fixed.proto`, `string.proto`, `bytes.proto`, `message.proto`,
`packed.proto`, `optional.proto`, `map.proto`) plus an end-to-end `compat.proto`
keeps each unit small, independent, and commit-able one family at a time. The
record test lives under `fixtures/src/test/java/<pkg>/<Family>Test.java` and the
proto under `fixtures/src/main/proto/`. The `:recordbuf-fixtures:genFixtures` task
auto-discovers new protos, so a new family is a `.proto` + a test class — no
build wiring per family.

### 3. Solve the same-simple-name class collision with a sibling `.ref` package

The protobuf-java `--java_out` for `Sample` and recordbuf's `Sample` want the
same simple name. Rather than runtime string-surgery, keep **two checked-in
protos per family**:

```
int.proto        package …fixture.i32;        option java_package = "…fixture.i32";
int-ref.proto    package …fixture.i32.ref;    option java_package = "…fixture.i32.ref";
                   option java_multiple_files = true;
```

Same shapes/field- numbers, different `java_package`. The `.ref` java_package
suffixes `.ref` + `java_multiple_files` so the generated reference lands in a
sibling package (`…i32.ref.Sample`), letting the test refer to it by
fully-qualified name:

```java
import bijnagte.recordbuf.fixture.i32.Sample;                 // the record
// reference: bijnagte.recordbuf.fixture.i32.ref.Sample       // FQN, no import clash
byte[] pb = bijnagte.recordbuf.fixture.i32.ref.Sample.newBuilder()...build().toByteArray();
assertArrayEquals(pb, Sample.Codec.encode(sample()));
```

`genFixtures` (a task in `:recordbuf-fixtures`) then runs one `protoc`
invocation with `--recordbuf_out` for the plain protos and `--java_out` for the
`.ref` variants, into the fixtures module's own generated source set (so both
trees are joined to fixtures `main` and therefore on the fixtures test
classpath).

### 4. Break the codegen circular dependency

The plugin must produce the generated sources, but the plugin itself is compiled
first. The classic same-module hack wires the *generated* code into the TEST
source set of the module under test and makes the generation task depend on that
module's `:jar` — a cycle that only ever works because of an ordering trick
(`:compileJava → :jar → :gen* → :compileTestJava → :test`).

recordbuf instead broke the cycle cleanly (KTD6): the interop/interface suites
live in a dedicated `:recordbuf-fixtures` module, and `genFixtures` invokes the
`:recordbuf-generator:installDist` launcher (the plugin as a separate, already-
built install) rather than `:jar` of the module under test. The generated record
+ protobuf-java reference compile into the fixtures module and the fixtures tests
consume that compiled artifact — so no module ever generates into its own
compiling source set.

## Why This Matters

Because the bug class is silent, the only reliable oracle is the reference.
Locking byte-equality against protobuf-java per family means a future regression
(any of the gotchas below returning) fails a test immediately, instead of
corrupting wire data in production. The per-family shape also makes each new
type family a ~10-minute unit: add the proto + test, wire nothing, run
`./gradlew test`.

## The wire-format gotchas this harness caught (each is a regression guard)

These are the real bugs the per-family interop tests surfaced; the family test
now guards each. Cited at the current tree:

- **Omit no field tags.** `Codec.encode` must write `<tag><value>` for every
  field, using `out.writeVarint(fieldTag(fieldNumber), v)` /
  `out.write* (fieldNumber, value)`. Forgetting the tag (writing raw values)
  silently corrupts the stream.
- **Fixed-width scalars are NOT varints.** `fixed32`/`fixed64`/`sfixed32`/
  `sfixed64`/`float`/`double` must use `readFixed*/writeFixed*`, not the varint
  path. `uint32`/`uint64` map to Java `int`/`long` (the sign bit is irrelevant
  to wire bytes — `writeVarint32(0x80000000, -2147483648)` round-trips).
- **Encode in ascending field-number order.** protobuf-java emits fields
  sorted by field number; the generator's encode loop must match (`CodecGenerator.java:73`
  sorts by `Field.number()`). Emitting in declaration order diverges from the
  reference whenever a `.proto` declares field numbers non-ascending — guard with
  an `order.proto` that declares `c=3, a=1, b=2` and asserts byte-equality.
- **proto3 presence / no `Optional<T>`.** In proto3, a singular scalar/enum
  reports `LABEL_OPTIONAL` from the compiler, so presence is decoupled: a field
  is `@Nullable` only when the raw `optional` keyword was set (`Field.isNullable()`
  at `Field.java:56` – `SCALAR, ENUM -> proto3Optional`). A singular MESSAGE is
  always present. Never box singulars into `Optional<X>` — `Optional<int>` does
  not compile; use `@org.jspecify.annotations.Nullable` instead.
- **Packed-repeated framing on JDK 25 / protobuf-java 4.36.2.** There are **no
  `writePacked*` helpers** on `CodedOutputStream` (verified via `javap`). Frame a
  packed group by hand: encode each element with the no-tag writer
  (`writeInt32NoTag`, etc.), then `out.writeByteArray(tag, body)`. Decode with
  `pushLimit(readRawVarint32())` / `while (in.getBytesUntilLimit() > 0) …` /
  `popLimit(_lim)` (`CodecGenerator.java:377`–`379`). `CodedInputStream` has no
  `getBufferedByteCount()` — use `getBytesUntilLimit()`.
- **Maps are repeated entry messages.** `map<K,V>` is `repeated MEntry{key=1,
  value=2}`; frame each entry length-delimited like a repeated nested message.
  Box both bounds (`Map<String,Integer>`), and the entry's key/value are written
  **unconditionally** (unlike a proto3 singular scalar, which skips
  default-valued fields).
- **`byte[]` content equality.** A record carrying a `byte[]` needs an explicit
  `equals`/`hashCode` (`Arrays.equals` / `Arrays.deepHashCode`); the JDK's
  implicit record `equals` compares arrays by identity. **Known limitation**
  (`CodeGenerator.java:157`): this handles a *direct* `byte[]` component only —
  `List<byte[]>` (a `repeated bytes` field) or `Map<?,byte[]>` still compare
  elements by identity. Wire encode/decode of those is correct; only the
  container's value-equality is not yet content-correct.
- **Declare `throws java.io.IOException`.** `Coded{Input,Output}Stream` throws
  checked `IOException`; propagate it on `encode`/`decode`.
- **Proto3 omits default-valued fields** on the wire; proto2 does not. The
  harness is proto3-only (proto2 presence was deferred).

## When to Apply

- Any protoc plugin whose generated output must be interop-compatible with a
  published protobuf runtime (not just round-trippable through its own decoder).
- Adding a new field/type family to a generator that already has the harness:
  add `<family>.proto` + `<family>-ref.proto` + `<Family>Test`, run
  `./gradlew test` — no per-family wiring.
- Reversing or refactoring a codec: the byte-equality oracle is what tells you
  you did not drift from the reference.

## Examples

Minimal per-family record (the `int` family):

```java
// fixture.i32.Sample (record) vs fixture.i32.ref.Sample (protobuf-java reference)
@Test void byteEqual() throws Exception {
    Sample x = new Sample(0x80000000);
    byte[] pb = bijnagte.recordbuf.fixture.i32.ref.Sample.newBuilder()
        .setA(0x80000000).build().toByteArray();
    assertArrayEquals(pb, Sample.Codec.encode(x));
}
```

The generated `Codec.encode` (what the harness proves correct):

```java
public static byte[] encode(Sample v) throws java.io.IOException {
  var baos = new ByteArrayOutputStream();
  var out = CodedOutputStream.newInstance(baos);
  if (v.a() != 0) out.writeVarint32(1, v.a());   // tag 1, varint
  out.flush();
  return baos.toByteArray();
}
```
