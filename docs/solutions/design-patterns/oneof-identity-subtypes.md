# Oneof identity subtypes: same-run, same-package generated messages and enums are the sealed-interface subtype themselves; every other case keeps an Unwrapable<T> wrapper

## Context

Before this change, every oneof case got a `<Member>Value` wrapper record
(`oneof_uint32` → `OneofUint32Value`), and the sealed interface carried the
member-access API: it `extends Unwrapable<Object>` with a `default Object
value() { return this; }`, so identity-shaped subtypes could inherit a
`value()` for free. The cost was that a message or enum that was *already* the
useful type had to be wrapped to appear in a oneof at all, and the interface's
`Unwrapable<Object>` was an erased, discoverability-poor API.

The goal: when a oneof case's member is a generated **message or enum**, make
that type itself the sealed interface's subtype — no wrapper — while keeping
the output deterministic even when generation is split across protoc
invocations.

## The rule

`IdentityCases.isIdentity(oneofFile, iface, member)` decides per (oneof, case)
pair. A case is an identity subtype iff all of:

1. the member is a generated message or enum (never a scalar, never a well-known type whose Java form is not generated by recordbuf);
2. the oneof's file **and** the member type's file are both in this invocation's `file_to_generate`;
3. the member type's Java package equals the sealed interface's Java package;
4. the member type is **not** the message that declares the oneof — the sealed interface is nested in the declaring record, and a class cannot implement its own member type, so a direct self-reference keeps its wrapper.

Every writer evaluates the same predicate on the same pair, so the case type's
`implements` clause and the interface's `permits` clause always agree, even
when generation is split across invocations (a pair whose files are not both
in the run falls back to the wrapper *on both sides* — silently, but
consistently, since both sides run the same predicate). Results are sorted, so
output does not depend on file order in the request.

A type may be identity in several oneofs at once (a `Part` record that is a
case of four oneofs implements four sealed interfaces).

The decision is observable: `IdentityCases` logs one DEBUG line per
wrapper/identity decision, with the rule branch that forced it (scalar, WKT,
self-reference, file not generated, package mismatch). Run the generator with
`-Dorg.slf4j.simpleLogger.defaultLogLevel=debug` to see it.

## Where `Unwrapable` lives

On the **wrapper**, not the interface. The sealed interface is a bare marker
(no `extends Unwrapable`, no `value()`). Each wrapper record implements
`Unwrapable<T>` with the member's **concrete** type — `Unwrapable<String>` for
a string case, `Unwrapable<Far>` for a cross-package message case — rendered by
`TypeRefs.unwrapableOf(memberType)`. Identity subtypes implement no `Unwrapable`
and are read as-is. Consumer dispatch:

```java
Object member = record.choice();                 // static type: the sealed interface
String value = member instanceof Unwrapable<?> u ? (String) u.value() : (String) member;
```

Why this shape (decided over the interface-level `Unwrapable<Object>` +
default `value()` that shipped first):

- The wrapper's `value()` is correctly typed (`Unwrapable<String>`, not an
  erased `Object`), which is discoverable from the wrapper's own signature.
- Identity types need **no** generated `value()` method: the codec, interop,
  and Avro converters already branch on `oneof.isIdentity(member)` at codegen
  time, so statically they know identity cases carry the member directly.
  Putting `value()` on the interface forced an explicit method onto identity
  records ("return `this`") whose only reader was user code — a method the
  codecs never called.
- The interface stays a marker, so "identity" is visible from the `permits`
  clause alone: a subtype that is not a `<Member>Value` record is an identity
  subtype.

## What didn't work

- **`Unwrapable` on the sealed interface with a default `value()`** (the first
  design): identity subtypes inherit `value()` for free, but identity types
  (messages, enums) then carry a method whose only reader is user code, and
  the interface API is an erased `Unwrapable<Object>`. Replaced by the
  wrapper-level design above at review.
- **Self-referential identity** (a `Node` as a case of its own oneof, `Node
  implements Node.Next`): the plan's early spike assumed Java accepts a class
  implementing its own nested interface type; the generated record does not
  compile. Rule 4 excludes it, and the wrapper (with its `Unwrapable<Node>`
  member) covers the case. Locked by `IdentitySubtypeTest.selfReferentialCaseKeepsItsWrapper`.
- **Rendering nested identity output against an "outermost-first" scope**: the
  `SourceRenderer` scope chain is innermost-first (`enterScope` prepends)
  despite the old javadoc, and `TypeRef.renderedInScope` had to drop a scope
  suffix for as long as the last dropped segment is still in scope — plus keep
  same-named-but-different-package top-level siblings qualified — before
  double-nested oneof components rendered unqualified names correctly. Header
  and `permits` clauses render with the declared type's own scope entry
  removed (a class's own members are not in scope inside its own header).

## How to apply

- Keep all oneof-shape decisions in `IdentityCases`; writers must not re-derive
  eligibility from local information. The fixture matrix for the rule is
  `fixtures/src/main/proto/identity.proto` + `identity_far.proto` (multi-interface
  message case, enum case, self-referential oneof, nested-message oneof,
  cross-package wrapper, scalar wrappers) with
  `fixtures/src/test/java/.../identity/IdentitySubtypeTest.java` locking
  identity, wrapper, wire, Jackson, and protobuf-java byte parity.
- New writer touching oneof cases: branch on `oneof.isIdentity(member)` the way
  `CodecSourceMapping` / `InteropSourceMapping` / `AvroConverterSourceMapping`
  do — identity binds the member directly, wrappers call `.value()` on the
  concrete wrapper type.
- A user-visible API change: `Pet.Kind.DogValue`-style wrappers disappear for
  identity cases (accepted as a pre-1.0 breaking change; no deprecated alias).
  See `docs/plans/2026-11-27-003-feat-oneof-identity-subtypes-plan.md`.
