# All-shapes Avro structural-twin generation

## Context

recordbuf's opt-in Avro bridge turns a generated record into a third-party-consumable
Avro type. Its v1 was a deliberate subset: it bridged only scalars, WKTs, and
repeated-scalars of the *first* top-level message, and **failed loud** on anything else
(oneof groups, map fields, nested or repeated non-WKT messages, `uint64`) — which the
bridge caught and turned into a silent skip of the whole file. The asymmetry was the cost:
one `.proto` file containing a single map field lost its *entire* Avro surface, while the
record side (the typed-field model) already represented every one of those shapes. The
structural twin closes the gap — a file with any of these shapes now gets a full Avro
output instead of none.

The full design rationale (requirements R1–R8, key technical decisions KTD1–KTD8) is in
`docs/plans/2026-11-17-012-feature-avro-structural-twin-plan.md`. This records how it was
realized, what didn't work, and how it is verified.

## Guidance

For every message and enum **reachable** from the bridged root (nested types, same-file
top-level siblings, and imported top-level messages — a referenced message gets its
triple even when its own file has the Avro option off), the generator emits three
artifacts into the type's own package:

- a `.avsc` — one Avro **protocol** document per bridged type: the reachable named
  records live in `types`, the root record is `message`;
- a **specific-record** class — `<Type>Avro` (e.g. `SampleAvro`), generated by Avro's
  `SpecificCompiler` over the `.avsc`;
- a **bidirectional converter** — `toRecord`/`fromRecord` mapping the record to that
  specific record field-by-field.

All three read one **name registry** (`AvroRegistry`) — a per-run map from each reachable
message to its Avro name and namespace (`nameOf` / `namespaceOf`; e.g. `Sample` →
`SampleAvro`, with short-name collisions disambiguated by the enclosing chain) — so the
`.avsc`, the specific class, and the converter can never disagree.

**The per-shape mapping** — the contract a third-party Avro consumer sees:

| Proto shape | Avro representation |
|---|---|
| scalar (except `uint64`) | the matching Avro primitive |
| `uint64` (any position: singular, repeated, map key/value, oneof case) | `long` — bit-exact two's complement |
| enum | `string` — the constant's name |
| well-known type | v1's WKT table, preserved verbatim |
| `map<string, V>` | an Avro `map` |
| `map<K, V>` (non-string key) | an `array` of a `{key, value}` record |
| oneof | a `null`-first union — `null` is the unset state, one member per case |
| singular / repeated message | the nested record, defined in the tree |
| `repeated X` | an `array` of X's mapping |
| unknown-field carrier | an always-present `unknownFields` array of `{number, wireType, value}` entries, 1:1 with the carrier |

Two representational choices carry the design:

- **`uint64` → `long`, bit-exact.** The record already models `uint64` as a
  two's-complement `long` for values ≥ 2^63 — the same contract a protobuf-java consumer
  faces — so an Avro `long` is the same 64 bits and the mapping is lossless with no
  special case (the converter passes a `long` straight through).
- **Enums → `string`.** Proto enums are open, but the record side coerces an undefined
  value to the first constant, so the bridge only ever sees named constants. Mapping to
  the constant's *name* string keeps the Avro side open — a newly-declared constant needs
  no schema change, and the converter resolves unknown names through the record-side
  `forNumber` fallback rather than failing.

A WKT with no static Avro schema (the dynamic `Struct`/`Any`/`Value`/`ListValue`, and the
v1-unmapped wrappers) still **fails loud** rather than silently dropping the file — the
record itself cannot represent those shapes, so the twin cannot either (see the WKT doc
under Related).

## What Didn't Work

- **Pivoting the `.avsc` to Avro's `Schema` model.** The generator emits the `.avsc` as
  hand-rolled JSON (a Jackson tree) and hands the *text* to `SpecificCompiler`. An attempt
  to build the document via `org.apache.avro.Schema` and let the library serialize it hit a
  dead end: the library's `Schema` JSON round-trip rejected the recordbuf-emitted document.
  The `.avsc` therefore stays hand-rolled JSON — do not route it through the `Schema`
  model, and do not add the `avro` runtime dependency just to render the document.
  *(per this session's testing; the generator does not put `avro` on its own main classpath
  for the document)*
- **Bringing the converter up to the full shape set.** The all-shapes `toRecord`/`fromRecord`
  lines had to be added per shape (map, oneof, repeated, nested message, enum, `uint64`,
  and the `unknownFields` carrier) rather than generalizing the v1 scalar lines. Each new
  shape's generated code must then clear the fixtures' gate set, which is exactly what
  makes the round-trip bar below the real regression guard.

## Verification

- **Fixture round-trip bar (R8).** `fixtures/.../avro/AvroInteropTest` locks the behavior
  per shape: `record → SampleAvro (SpecificRecord) → record` full equality; the ≥ 2^63
  `uint64` arriving bit-identical; a oneof whose message case carries non-empty unknowns
  returning them 1:1; and an undefined-enum name resolving through `forNumber` instead of
  throwing. Every emitted `.avsc` parses with real Apache Avro.
- **R22 — the record stays Avro-free.** A generated `.rec` record carries no
  `org.apache.avro` import; only the `<Type>Avro` specific class and the `.avsc` do. The
  bridge is one-directional in its dependencies: record → Avro, never the reverse.

## Why This Matters

A file with any of the previously-rejected shapes no longer loses its whole Avro output —
the bridge is a genuine structural twin of the record, so Avro-native consumers get exact,
typed, queryable data (real records, maps, arrays, and unions) rather than a partial view
or an opaque payload. The record side is untouched (it remains Avro-free), and the
name-registry single-source-of-truth keeps the three emitted artifacts coherent.

## When to Apply

- Extending the Avro bridge with a new field shape: add its mapping to the `.avsc` tree,
  the specific-record emission, and the converter, all through the shared name registry.
- Choosing a representation when a shape has more than one Avro option: use the table.
- Investigating a broken or missing Avro output: check the shape against the table and the
  round-trip bar, and remember the fail-loud gate only fires for genuinely unmappable input.
